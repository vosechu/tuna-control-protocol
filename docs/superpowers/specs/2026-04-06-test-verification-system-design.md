# Test Verification System Design Spec

**Date:** 2026-04-06
**Status:** Mostly built — see "Implementation Status" (status confirmed accurate by 2026-04-07 triage)
**Related rule:** `.claude/rules/llm-test-verification.md`
**Related plan:** `docs/superpowers/plans/2026-04-07-stash-recovery-and-cleanup.md`

## Goal & Motivation

LLMs are excellent at writing tests that *look* correct but don't actually test anything. Common failure modes observed:

- Tests with no assertions that "pass" by virtue of GUT counting zero asserts as success
- Tests that assert on mock return values rather than real behavior
- Tests with names that don't match what the assertions check
- Tests reimplementing production logic in helpers and testing the helpers
- Tests that pass even when the production code they claim to exercise is deleted

The goal of this system is to make test verification *tamper-evident*. After a test passes a structured verification process, a hash is computed and stored alongside the test. If anyone (human or LLM) modifies the test or the file containing it, the hash breaks and CI blocks the commit.

This is the bridge between "trust the LLM wrote good tests" and "have proof it followed a real verification process."

## Architecture

Four artifacts work together. Each has one job.

### 1. The checklist — `.claude/rules/llm-test-verification.md`

A 5-phase structured workflow the agent follows when writing or verifying tests. Path-gated to load when touching any test file. Phases:

1. **Identify test candidates** — list test functions with descriptive behavior names
2. **Red-green-refactor** — per-test cycle: write test, confirm fail, write code, confirm pass, mutate code, confirm test catches mutation, restore
3. **Test quality review** — name/assertion match, no trivially passing, no duplicates, not testing mocks
4. **QA agent review** — dispatch the QA agent to find missing edge cases and brittle tests
5. **Stamp** — run the stamp script to seal the result

The detailed checklist is the operational reference. This spec describes the system; the rule file describes the steps.

### 2. The stamp script — `script/stamp_tests`

A dumb write operation. Takes a test file path, computes hashes, writes a sidecar `.gd.stamp` file. Does NOT run tests, does NOT verify anything, does NOT enforce that the checklist was followed. The verification *already happened* through Phases 1-4 of the checklist. The stamp is just the seal on the result.

```bash
script/stamp_tests tests/unit/test_curiosity_tracker.gd
script/stamp_tests --all   # stamp all test files
```

The script is intentionally simple so that the trust is in the *process*, not the script. If the agent skips the verification cycle and just runs `stamp_tests`, the stamp will be valid but the test won't actually verify anything. The honesty depends on the agent following the checklist, not on the script catching cheaters. CI catches the absence of stamps; humans catch sloppy verification during code review.

### 3. The verify script — `script/checks/verify_tests`

A read operation. Three checks, in order:

1. **Stamps exist** — every `tests/**/test_*.gd` has a corresponding `.gd.stamp` sidecar
2. **No orphans** — every `*.gd.stamp` has a corresponding `.gd` file
3. **Hashes match** — for each stamped file, the file hash and per-test hashes match the current contents

Exits non-zero if any check fails. Lists exactly which files/tests need attention and what action to take (run `stamp_tests`, delete an orphan, etc.). Used by CI and pre-commit. No arguments — checks everything.

### 4. The stamp file — `*.gd.stamp` sidecar

A YAML file alongside each test file. Committed to git. Format:

```yaml
# AI-DEV: AI **MUST NOT** edit this file. It is generated by the verification
# process defined in .claude/rules/llm-test-verification.md. If a stamp is
# invalid, re-run the full verification process — do not manually update hashes.
file_hash: 313d2c10
verified_at: 2026-04-05T19:43:11Z
tests:
  test_visiting_new_cell_is_novel: a864ea0d
  test_revisiting_within_cooldown_is_not_novel: 9637f6e0
```

Hashes are the first 8 hex chars of SHA-256. Per-test hashes cover the function body excluding the AI-DEV marker line (so the marker can be added/updated without invalidating the hash). The file hash covers the whole file.

The AI-DEV note at the top references the rules file, not the stamp script — the rules file is the source of truth for "how do I make a valid stamp," not the script.

## Trust Chain

```
Checklist (rules file) — agent does the work
    ↓
Artifacts (test file, AI-DEV markers, QA agent review)
    ↓
Stamp script — seals the result with hashes
    ↓
.gd.stamp sidecar — committed to git
    ↓
Verify script — pre-commit and CI check the seal
    ↓
Commit proceeds (or is blocked)
```

The weakest link is steps 1-3 (the agent following the checklist). The hash only proves the script ran, not that the checklist was thorough. This is acceptable because:

1. The hash compresses 8+ verification steps into 1 enforceable artifact
2. CI reliably catches the most common failure (no verification at all → no stamp)
3. Code review can spot sloppy verification when humans look at the diff
4. Future tampering with verified tests is mechanically detected

## Stamp File Format

### Hashing rules

- **File hash:** SHA-256 of the entire file contents, first 8 hex chars
- **Test function hash:** SHA-256 of the function body (lines from `func test_*` through the next top-level statement), excluding any line containing `# AI-DEV:`, with trailing whitespace stripped, first 8 hex chars

### Why exclude AI-DEV lines from per-test hashes?

So an agent can add or update the AI-DEV marker on a test that was already stamped, without invalidating the per-test hash. The file hash will catch the change (forcing a re-stamp), but the per-test hash logic is consistent regardless of marker presence.

### Why include the file hash AND per-test hashes?

The file hash catches any change to the file — whitespace, helpers, comments, imports. The per-test hashes catch surgical edits to specific functions and let `verify_tests` produce precise error messages ("test X has changed" vs "the file has changed somewhere").

### Why a separate sidecar instead of inline markers?

Two reasons:
1. **Tamper resistance.** An agent editing a single test file can't accidentally update both the test and its hash in lockstep — the stamp is in a different file, updated by a different script.
2. **Diff visibility.** Stamps appear next to test changes in PRs, making it obvious which tests were re-verified vs. which were modified without verification.

### Why per-file stamps instead of one central registry?

Conflicts. A central `tests/.test_registry.yaml` would conflict every time two branches added or modified tests. Per-file stamps only conflict when two branches modify the same test file — which is a real conflict that needs human attention.

## Integration Points

### Pre-commit hook

`script/pre_commit` should call `script/checks/verify_tests`. Failure blocks the commit with a message naming the specific files/tests that need attention.

**Status:** Not yet implemented. The pre-commit hook exists but does not call verify_tests.

### CI / `script/validate`

`script/validate` runs all checks in `script/checks/`. Once `verify_tests` is in that directory, it runs automatically as part of CI.

**Status:** The script is in the right place but `script/validate` doesn't currently include it because doing so would fail CI on every existing un-stamped file. Needs a transition plan (see "What's Left").

### Mutation testing

Phase 2 of the checklist requires mutating the production code and confirming the test catches it. There is no GDScript mutation framework, so this is manual. The agent picks the mutation, runs the tests, restores.

**When a mutation survives:** This is information, not necessarily a test failure. Single mutations can survive because:
- The production code uses defense-in-depth (two independent guards both catch the mutation)
- Multiple tests cover the same code path (only the targeted test failing isn't necessary)
- The test catches a different aspect of the same code (e.g., scoring formula vs. branch logic)

The agent should report surviving mutations and move on. The test isn't necessarily bad — the production code might be deliberately redundant. Forcing the test to fail by removing the redundancy would *weaken* the production code, not strengthen the test.

Documented examples from Phase B verification:
- `test_arm_ignores_can_beyond_reach` — survived single mutations because both `score_ad` distance check AND the `ARM_REACH_RU` gate independently block targeting. Required a compound mutation (disable both) to fail.
- `test_adjacent_slots_connected` — survived removing the WALK edge because cats can route through floor nodes. Test was reframed to assert path length == 2 (direct connection), not just `> 0`.
- `test_transitions_when_score_exceeds_commitment_plus_threshold` — boundary mutation `<` → `<=` survived because the test used `SWITCH_THRESHOLD + 1`, which passes both predicates. Test was extended with explicit boundary cases.

### Lesson from the 2026-04-07 triage

Stamping a test file does *not* protect the relationship between the test and the production constants it asserts against. When the production code changed scale, the stamped test went stale silently — the stamp still verified, the assertions still ran, they just compared against the wrong numbers. This is a known limitation, not a bug:

- The stamp verifies the test file's *content* hasn't changed.
- It does not verify that the production values the test asserts against haven't changed.
- A failing test on a stamped file is the correct signal — the agent should investigate, fix one side or the other, then re-stamp.

The bad outcome would have been: someone re-stamps the stale file without fixing it, sealing the wrong assertions. The verification process's "Phase 2 mutate the production code" step is supposed to catch this, because mutating the new constants would still pass the old asserts. Add this to the QA review checklist: when re-stamping a previously-stamped file, confirm Phase 2 mutation testing was actually re-run, not skipped because "the file already had a stamp once."

## Known Limitations

### Helper file changes don't invalidate stamps

If a test imports a helper or fixture file and the helper changes, the test's hash doesn't break. The test could now behave completely differently and the stamp would still be valid. This is a real gap. Mitigation:

- Tests should minimize helper dependencies
- When a helper changes, manually re-stamp the dependent tests (the agent's responsibility, not enforced)
- Future enhancement: track helper file hashes per test (not in v1)

### Mutation testing is manual

Phase 2 step 9 ("mutate the production code") relies on the agent picking a good mutation. Quality varies. There is no GDScript mutation framework. This is the most judgment-heavy step in the process. Mitigation: the post-stamp code review catches obvious cases where the mutation was too narrow.

### Hash computation must stay stable

The `stamp_tests` and `verify_tests` scripts must compute hashes identically. They share helper functions for `get_test_functions`, `get_function_body`, and the SHA-256 truncation. If these drift, every existing stamp becomes invalid. Mitigation: the helper functions live at the top of both scripts and should be kept in sync. Future: extract to a shared bash include.

### "GUT class_names not imported" intermittent failure

The `script/checks/gut_tests` wrapper script occasionally fails with `Some GUT class_names have not been imported` even when tests pass via direct Godot invocation. Not a stamp/verify issue, but it affects the agent's ability to run tests during Phase 2. Workaround: invoke Godot directly. Real fix needed in `gut_tests` script.
